# Frontend readiness (Phase 5.5)

Generated by `python -m src.modeling.phase5_5_report`. No frontend was built and no API was deployed.

## The interface

```python
from src.modeling.prediction_api import forecast_prospect, validate
f = forecast_prospect(name='Fernando Mendoza', draft_year=2026, mode='pre_draft')   # or mode='post_draft'
f = forecast_prospect(cfbd_player_id='4606194', final_season=2024)                  # any college passer-season
f = forecast_prospect(name='Fernando Mendoza', draft_year=2026, mode='post_draft', assumed_pick=40)  # hypothetical
assert validate(f) == []

from src.modeling.historical_backtest import historical_backtest
b = historical_backtest('Josh Allen', 2018)
```

CLI: `python -m src.modeling.prediction_api --name "Fernando Mendoza" --draft-year 2026 --mode pre_draft [--json]` and `python -m src.modeling.historical_backtest --name "Josh Allen" --draft-year 2018 [--json]`.

* Pure Python, local artifacts and cached data only: no network calls.
* Returns a plain `dict` that is JSON-serialisable (checked by `validate`). That maps directly onto a FastAPI response model.
* `schema_version` = `1.0.0`. Bump it whenever a field changes meaning.
* Every block has `status` (`available` / `unavailable`); an unavailable block carries `reason` and no numbers. Top-level `partial` lists the unavailable blocks.
* Every number is labelled `observed`, `predicted` or `historical_descriptive`, with its model version.

## Output structure

```text
schema_version, status, mode, partial
player:       name, college, draft_year, final_college_season, identifiers{qb_draft_prospect_id, cfbd_player_id, gsis_id},
              identity_verification, actual_draft{label=observed, drafted, round, overall_pick}
draft:        probability{status, pre_combine, post_combine, post_combine_note, population, model_version, backtest}
              round{groups{Round 1, Rounds 2-3, Rounds 4-7}, rounds{1..7}, expected_round, conditional_on, display_note}
              pick{median, interval_50/80/90, measured_coverage}
              eligibility{population_status, in_verified_universe, classification}
career:       mode, hypothetical, assumptions[], model_version
              start_probabilities{p_16_plus, p_32_plus, p_64_plus (nested), p_any_nfl_game, method}
              five_year_totals{stat: expected, interval_50/80/90, model, interval_method, measured_coverage}
              year_by_year{status, seasons[1..5]{stat: expected, interval_80}, method}
              reference_v2_p32, efficiency_note
comparisons:  kind=explanatory, comps[5]{name, college, draft_year, round, overall_pick, distance,
              closeness_index_heuristic, most_similar_on, biggest_differences, nfl_outcome{label=observed, ...}}
uncertainty:  model_versions, calibration_status, training_coverage, data_limitations[]
```

## Unsupported requests return structured statuses

| Situation | What the interface returns |
|---|---|
| QB outside the verified draft population (underclassman, unknown eligibility, final season not verifiable yet) | `draft.probability.status = unavailable` with the population status; round and pick "if drafted" still shown |
| Combine for that draft year not in the data | `post_combine = null` with a note; `pre_combine` still shown |
| `post_draft` without a pick (undrafted, or no record) | `career.status = unavailable`, reason says to pass `assumed_pick` |
| More than half of the career features missing | `career.status = unavailable` |
| Simulation reference tables missing (fresh clone) | `year_by_year.status = unavailable` with the regenerate command; five-year totals still work |
| Comparison pool missing | `comparisons.status = unavailable` |
| Unknown player | top-level `status = unavailable`, `reason` |

## What the API layer will need

* Load the engine once at startup (`prediction_api.engine()` is cached). The first call reads the SQLite database and parquet files; later calls take well under a second without the year-by-year simulation.
* Search endpoint: the identity tables (`qb_draft_prospects`, CFBD passer-seasons) give name, school and years for typeahead. Not built yet.
* Precompute forecasts for every listed prospect if latency matters; inputs change only when the data is refreshed.
* Data files are gitignored (player-level CFBD/nflverse data). A deployment needs a data build step (README, "Data that is not in Git").
* Display rules the frontend should follow: show round **groups** rather than single rounds; show intervals whenever a point forecast is shown; never show the closeness index as a percentage chance; label post-Combine draft probability as participation-driven; show the efficiency note instead of efficiency forecasts.
